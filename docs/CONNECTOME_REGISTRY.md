# Research connectome registry service

`createConnectomeRegistry` is the service adapter for explicitly selected, locally pinned connectome workers. The full-connectome HTTP and browser paths use it through the separate research catalog; it is not the synthetic habitat identity store. No full graph was run to validate this change. The existing synthetic fixture remains separate; unsupported worker/data states never substitute it.

Construction takes trusted identity records `{individualId,dataset,directory,checkpoint?,checkpointId?}`, a capacity policy, `getResources`, an atomic `persistCheckpoint` callback, and optionally a worker factory for numerical tests. Records are immutable mappings to exactly `male-cns:v1.0` or `banc:v888`; individual identity is independent of dataset neuron IDs. No directory, checkpoint arrays or credentials appear in public registry snapshots. Constructing, listing and observing the registry never loads a worker or creates an individual. Durable identity creation/catalog selection remains the caller's responsibility.

Explicit `load(id)` opens one paused worker. All loads serialize globally; same-individual operations also serialize, so concurrent browser requests cannot create duplicate workers or overbook a known resident ceiling. Admission merges service reservations (including loading, paused, faulted and stopping workers) with caller-reported residents. `getResources({individualId,dataset})` supplies fresh aggregate and free memory, external resident inventory and a trusted `measurement:{backend:'connectome',dataset,incrementalMemoryBytes,includesCheckpointSerialization:true}`. The incremental estimate must come from a separately bounded measurement for this profile/configuration and account for checkpoint serialization/staging. The service does not invent a graph memory estimate, sample a full neural graph or accept fixture evidence as connectome evidence. Missing/incorrect evidence fails closed. A caller must not expose this trusted evidence field as an arbitrary browser override.

`command(id, envelope, checkpoint?)` uses exactly `{protocolVersion:1,individualId,sessionEpoch,commandSequence,action,steps}`. Sequence starts at zero for each explicit load and must match the current snapshot; it increments once a valid command is attempted, including failure, so a timed-out action cannot be retried ambiguously. Worker epoch rotates on restore/reload. Queue validation happens when a command executes, rejecting stale queued epochs. `steps` is null except `advance`, which allows 1–1000 fixed 1 ms neural steps. The separate checkpoint argument is required only for restore. The registry exposes no numerical probe operation.

- `start`: permits explicit advancement, but advances zero time itself.
- `advance`: the only command that advances neural time, while running.
- `pause`: pauses and retains all neural state.
- `rest`: pauses with a distinct resting service status; this research model has no optional chemistry to cancel.
- `home`: pauses locally, with an explicit disclosure that no external body/travel exists.
- `save`: pauses, exports supported state, and selects the newly written durable head.
- `unload`: pauses and saves before releasing the worker; write failure keeps the worker resident and paused.
- `restore`: pauses, captures a rollback checkpoint, commits the staged worker candidate paused under a fresh epoch, then selects the durable target; a pre-selection persistence failure rolls the worker back, while uncertainty retains the reported selected head only in a recovery-required paused service.

## Durable writer contract and restore boundary

`persistCheckpoint({individualId,dataset,parentId,checkpoint,operation})` must atomically persist checkpoint data, lineage and selected head; it returns `{checkpointId}` only after commit. On rejection it must leave both data/head selection unchanged. This injected contract is mandatory, not an in-memory fallback. The adapter changes its saved head only after successful acknowledgement. The caller must include this registry's records and heads in its backup format before enabling persistence in the app.

The sparse kernel now has instance-local `prepareRestore`/`commitRestore` capabilities. Preparation validates every state field and allocates all replacement arrays without changing live state. The worker exposes one opaque staged token bound to its current session; any intervening mutation is rejected until the token is explicitly committed or discarded. Read-only snapshot/checkpoint queries do not invalidate it. The registry reserves the complete membership, drains already queued work, and blocks samples, lifecycle commands, joins, barriers and shutdown from invalidating a staged transaction. A failed preparation explicitly discards every worker candidate. A pre-selection worker or writer failure rolls committed workers back to captured paused checkpoints; if rollback itself fails, the worker is evicted. A post-rename durability uncertainty reports the complete selected-head map, sets recovery-required state, evicts affected workers, and blocks service mutations until storage recovery.

Worker calls and loads have a configured deadline (default 30 seconds, maximum 120 seconds). The real `openConnectomeBackend` opening promise exposes `terminate()` and `terminated` before readiness, allowing the registry to stop a worker still loading source data. A timeout requests shutdown and retains its resident admission reservation until termination is confirmed. The public status is `stopping` during this interval; another load cannot reuse that slot. Injected legacy factories without a pre-ready termination handle keep their reservation until the opening settles and the resulting backend's `close()` completes. A rejected injected opening must clean up its own resources.

The factory receives an `onExit` callback. A real spontaneous worker exit immediately clears live neural telemetry, rotates the public epoch and reports `unavailable` with the durable recovery head retained; no follow-up command is needed. Exit callbacks are scoped to a unique owner record, so an old worker cannot revoke a replacement. Only confirmed exit releases capacity. Late opening completions are closed without publication. Persistence callbacks are not detached on a timeout because their durable commit outcome cannot safely be abandoned; they must settle under their storage implementation's own contract. `close()` refuses new submissions, drains already accepted per-ID operations, and stops workers. It is **not an implicit save**: callers must explicitly save/unload first to retain unsaved progress. Startup/recovery never replay elapsed downtime.

## Evidence

`node --test server/connectome-registry.test.js server/sparse-checkpoint.test.js server/connectome.test.js` runs small actual sparse-LIF graph sessions under both exact namespaces, preserving the independent numerical-reference tests. Service coverage includes no-load observation, serialized capacity, cross-individual isolation, save/unload queues, malformed restore, writer failures, failure after durable commit, stale prepared tokens and late worker loading. Additional regressions cover timed-out opening and slow-close admission retention, stale exit callback isolation, actual Worker exit notifications without polling, and termination of the real backend Worker before readiness. Test measurement values are injected fixtures, not operational memory measurements. No claim of measured full-dataset registry capacity, biological learning, neural body control, retained chemistry or supported embodiment is made.

## Lazy catalog integration

`register(identity)` explicitly adds trusted `{individualId,dataset,directory,checkpointId?,checkpoint?}` metadata while preserving all existing residents. It never opens a worker, caps registrations at 64, rejects duplicate IDs (including attempted profile replacement), and refuses closed/closing registries. Catalog creation and registration remain distinct owner actions; the HTTP layer should register the metadata returned by a successful catalog create.

An optional `loadCheckpoint({individualId,dataset,checkpointId})` callback loads the selected saved head only on explicit load, after capacity admission and before worker construction. Missing/foreign payloads fail rather than becoming fresh initial state. When configured, successful saves retain only the returned head ID in registry metadata and reread that exact head on reload; historical payload arrays stay in immutable store files. No callback runs for a fresh identity with a null head. Records with a saved head but neither payload nor callback are rejected at registration.

The restore signature is `command(id,envelope,checkpoint,sourceCheckpointId)`. The fourth argument is required when using the durable lazy store and is forwarded to `persistCheckpoint` as `sourceCheckpointId`; save/unload pass null. The store must validate the exact source belongs to the recipient and its bytes/hash match the requested restore payload. Equivalent checkpoints must never silently change the requested lineage source.

## Uncertain selected-head durability

A trusted writer can report `CONNECTOME_DURABILITY_UNCERTAIN` when catalog selection changed but its parent-directory sync failed. The error must include the matching `individualId` and validated `selectedCheckpointId`; joint operations also provide `selectedHeads` for every affected identity. The registry retains every known selected head in metadata, exposes `recoveryRequired:true`, and evicts affected workers rather than reporting a successful operation or pairing cached arrays with uncertain storage. The service blocks new loads and mutations while recovery is required, and a lazy loader refuses activation until storage has been closed and successfully reopened; only then can an explicit load recover a selected payload paused. Without a durable loader, or if the uncertain error reports an invalid/foreign identity/head, rebuild the registry from recovered storage metadata. Cached arrays cannot bypass this recovery boundary.

Focused tests cover uncertain save/unload/restore selection, failed reload before recovery, exact paused recovery afterward, and foreign/incomplete writer receipts. The existing pre-selection writer failure contract still preserves the old head and current paused arrays.
