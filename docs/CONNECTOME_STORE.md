# Durable research connectome catalog

`openConnectomeStore(directory,{profiles,catalogCapacityBytes})` supplies a durable identity catalog and atomic checkpoint writer to the research registry. It creates no worker, advances no neural time, and cannot substitute a synthetic fixture. `catalogCapacityBytes` is a bounded deterministic test/embedding override and cannot exceed the documented catalog ceiling. This is a separate service module; the existing fixture identity/backup format is unchanged.

## Trusted profile configuration

Each allowlisted exact dataset (`male-cns:v1.0` or `banc:v888`) requires a server-supplied descriptor `{directory,graphSha256,manifestSha256,neuronCount,edgeCount}`. The directory is local configuration and is never persisted in the portable catalog. Graph/model/provenance descriptors are pinned in each individual record; opening with a changed descriptor fails before activation. The caller must derive these values from verified local graph acquisition/measurement. Browser input cannot supply or override them. Missing descriptors leave creation unavailable; no full graph is loaded to manufacture one. Descriptor tests use deliberately tiny graph fixtures, not operational measurements.

`create(dataset)` explicitly allocates a fresh stable UUID with immutable dataset/graph/model identity and returns saved-unloaded metadata. It allocates no neural arrays and has no initial checkpoint; the first explicit registry load initializes the exact research kernel paused. Unknown profiles, duplicate writer ownership, capacity limits and incompatible existing files reject. A missing catalog in a nonempty directory is never treated as permission to initialize or erase it.

`identities()` returns `{individualId,dataset,directory,checkpointId}` metadata for registry registration. `readCheckpoint(individualId,checkpointId)` loads and validates one immutable file; IDs are UUIDs mapped to fixed filenames, never paths. `checkpoints(id)` returns bounded lineage/hash metadata. Call these only through trusted recipient routing; directory metadata is not intended as public browser telemetry.

## Persistence transaction

Wire `persistCheckpoint` directly to the store method. It accepts `{individualId,dataset,parentId,checkpoint,operation,sourceCheckpointId?}` where operation is save, unload or restore. The selected parent must still match the catalog head. Validation checks exact fields, recipient, dataset, engineered model parameters, graph SHA, array dimensions, finite voltages, refractory/pending-spike consistency, safe clocks and feasible cumulative counters. These rules mirror the sparse kernel checkpoint contract and are tested against actual tiny-kernel exports for both profiles.

A successful transaction writes an exclusive UUID-named checkpoint file, fsyncs it and its directory, then atomically replaces the catalog with a new selected head and fsyncs the catalog directory. Checkpoints are never overwritten or deleted. The catalog has its own SHA-256 checksum and contains only metadata; every referenced file has a byte count and hash. Startup verifies one checkpoint at a time and retains no historical neural arrays in memory. Atomic catalog replacement uses a same-directory temporary-file/fsync/rename/directory-fsync sequence; durability remains subject to filesystem/platform guarantees.

Restore appends a new head whose parent is the previously selected head and whose `restoredFrom` points to the explicitly requested `sourceCheckpointId`, required for restore and absent/null otherwise. That exact source must belong to the same individual and match both payload hash and bytes. Absent, foreign or mismatched sources are refused. Equivalent payloads in other history entries do not alter the selected lineage source. No recorded credentials, elapsed downtime, learning, chemistry or body state are created by this store.

Write failure before catalog selection preserves the previous head and catalog. Ordinary immutable files written before a failed individual write remain inert orphans. Joint restore staging is different: every staged restore writes a durable transaction manifest first, removes only its transaction-owned unreferenced files on cancellation/failure/close, and recovers those manifests on reopen. Unrelated orphan files are preserved and still count toward storage bounds. The registry pauses on writer failure; after a successful durable selection followed by worker loss, it can explicitly reload the selected head paused. A custom `writeCatalog` test/embedding hook must retain the same atomic rejection contract; it is not an arbitrary browser extension.

`persistJointCheckpoint` stages and validates every member checkpoint before replacing one schema-2 catalog. A joint record contains the 5 ms interval, world tick, stable member IDs, dataset/graph/model namespaces, checkpoint IDs and hashes, simulation clocks and active/resting modes. Both joint save and restore project the current physical checkpoint-file inventory plus every planned immutable file and refuse before writing when the 8192-file ceiling would be crossed. `prepareJointRestore` performs the complete source, history, byte and catalog-capacity checks, writes and fsyncs every staged restore file under a durable transaction manifest, and returns an unselected transaction. `commitJointRestore` rechecks the expected heads and selects all restore lineages in one catalog replacement. A failed pre-commit write removes only transaction-owned staged files; a post-rename durability uncertainty preserves the complete selected-head map and remains fail-closed until reopen. The fixture identity store remains a separate catalog. A heterogeneous fixture/connectome coordinator is not implied by this catalog-local transaction. The separate [cross-catalog coordinator](CROSS_CATALOG_CHECKPOINTS.md) defines that contract, but no adapter binds it to this store yet.

Bounds: 64 individuals, 64 checkpoint entries per individual, 64 joint records, 2 MiB catalog, 16 MiB per checkpoint, 1 GiB aggregate checkpoint files (including orphans), and 8192 physical checkpoint files. File-count refusal is projected before any new immutable file is written. Staged restore manifests are transaction-owned recovery metadata, not checkpoint payloads; reopen removes only unreferenced files listed by a valid manifest. Hitting a bound refuses new work without deleting unrelated history. A SQLite exclusive writer lock in this separate directory follows the fixture store's existing OS-backed lock pattern and releases on process death. Reads refuse symlink checkpoint/catalog/staging files and store/checkpoint/staging directories. The store does not serialize full histories into one JSON payload.

## Backup and offline recovery contract

`store.backup(freshDestination)` copies the coherent committed catalog plus **every referenced checkpoint file**, including non-head history required by restore lineage. It excludes worker state, private directory configuration, the writer lock and inert orphan files. Checkpoints are immutable and verified while copying. The catalog is written last; an interrupted copy lacks a complete valid catalog and cannot be opened as an empty replacement store. Failed partial copies are left intact for operator inspection; rerunning requires another fresh destination. Existing destinations are never overwritten or merged.

`restoreConnectomeBackup(source,freshDestination,{profiles})` verifies the entire catalog, descriptors, bounds and all referenced checkpoint hashes/state before creating the new destination. It then copies one file at a time and writes the catalog last. The trusted local directory mapping must be supplied again; it is not imported from a backup. The restored result is offline, with no worker/resume/replay. Corruption leaves the source and any preexisting destination unchanged.

The fixture backup command does **not** yet include this separate catalog. A future application backup bundle must explicitly include its catalog plus all referenced files, validate both backend sections before selecting a destination, and preserve independent profile identity. Never call a fixture-only backup a complete connectome backup. The dedicated methods above already implement coherent standalone inclusion/recovery.

Validation: `node --test server/connectome-store.test.js` covers independent profile identity/reopen, writer exclusion, unknown/nonempty paths, create/save/restore failures, history/catalog/file capacity refusal, inert orphan recovery, numerical/model/graph rejection, explicit restore lineage, stale parents, corruption/symlinks, schema-1 compatibility, joint staged durability refusal, projected 8192-file refusal, transaction-owned staging cleanup/recovery, complete selected-head reporting, and complete history backup/restore. No full graph or production state is accessed.

## Uncertain durability and path boundaries

A failed write before catalog selection still preserves the prior head. If directory fsync fails **after** the rename, the catalog already selects the new head: the store keeps that actual selection in memory and throws `CONNECTOME_DURABILITY_UNCERTAIN` with the validated `individualId`, `selectedCheckpointId`, and, for a joint transaction, `selectedHeads` for every affected member. It never claims the old head remained selected. Metadata reads can identify the selected head, but further writes, payload activation and backups fail with `CONNECTOME_STORE_RECOVERY_REQUIRED` until the store is closed and successfully reopened. Reopen validates every referenced file and confirms the catalog directory sync before allowing activation.

The registry must treat that specific error as an uncertain committed selection: retain every reported selected head in metadata, set `recoveryRequired`, and evict affected workers rather than pairing cached arrays with an uncertain catalog. The service blocks new loads and mutations while recovery is required. An explicit reload must obtain the selected payload through the recovered store's lazy loader. Integrations without a durable loader, or errors without a valid recipient/head, must reconstruct the registry from recovered metadata rather than reuse cached arrays. Recovery always loads paused.

Backup and restore reject destinations equal to or underneath the source before creating anything. Existing symlink ancestors are resolved for this check, so aliases cannot insert a backup directory into the authoritative checkpoint directory. Copy completion flushes the copied checkpoint directory, catalog directory and destination parent. Tests cover direct and symlink-overlap rejection while preserving subsequent source saves and recovery.
