# Full-connectome shared research barrier

This increment adds a separate, explicit research path for already loaded MaleCNS v1.0 and BANC v888 identities. It does not extend the synthetic fixture renderer, create a body controller, supply retinal pixels, attach chemistry, enable retained learning, compare biological sex, or provide a cloud fallback. A shared participant is a real sparse-LIF worker with its pinned graph namespace and checkpoint lineage.

## Boundary

The existing fixture shared garden remains unchanged. The new path is available at `/api/connectomes/shared` and is shown in the full-connectome lab as a research barrier. It requires two to 64 already loaded, admitted research residents; join does not create, load, reset, crop, or replace an identity. The configured resident ceiling and trusted per-profile memory evidence still apply at load time.

The world interval is 5 ms. Each active full-connectome participant receives exactly five explicit 1 ms sparse-LIF substeps per complete barrier. The service waits for every participant, validates each prepared candidate before committing, and rolls every committed candidate back to its in-memory pre-barrier state and pauses the group if a worker reports a failure. A worker that cannot be rolled back is evicted with its durable checkpoint retained; no skipped or extra neural time is reported as success.

Completion order is not an authority. The public traces are returned in the requested membership order, include the stable individual ID and session epoch, and report the exact substep count and before/after clocks. The path has no observation payload, so there is no way to inject a partner's neural state, hidden target, camera metadata, or action into another worker.

## Lifecycle

`POST /api/connectomes/shared/join` accepts exact membership envelopes containing `protocolVersion`, `individualId`, `sessionEpoch`, and the current individual `commandSequence`. Joining pauses all members and creates a new shared ID and world epoch. `POST /api/connectomes/shared/:id/control` supports explicit `start`, `pause`, `save`, and `separate`. `POST /api/connectomes/shared/:id/barrier` runs one complete barrier and advances the shared sequence only after all participants commit. `POST /api/connectomes/shared/:id/member` supports per-member `rest`, `resume`, and `withdraw`; withdrawal stops at the two-member floor and records the boundary. `GET /api/connectomes/shared/checkpoints` lists bounded joint records. `POST /api/connectomes/shared/restore` can be selected independently of a live shared session, but requires the complete saved membership, current paused envelopes, and exact saved dataset/graph/checkpoint lineage; it creates fresh worker sessions and returns a paused shared session, or `resting` when every saved member is resting. It never starts a simulation.

Reads and mutations use the existing same-origin, host, content-type, and bounded JSON checks. Joining invalidates individual command envelopes, while the ordinary individual research command route refuses lifecycle control for a joined identity; separation and withdrawal invalidate the affected envelopes again. The full-connectome lab displays the research-only disclosure and never presents this path as a garden body or sensory result.

## Persistence and remaining work

The connectome catalog now supports a schema-2 joint record for a full-connectome-only shared session. A paused explicit save validates every member checkpoint and replaces all selected heads and the joint record in one catalog commit. Restore preparation validates complete membership, source hashes, history, byte/catalog bounds and the projected 8192-file inventory, writes and fsyncs staged immutable restore files under a transaction manifest, and reserves the members before any worker candidate is prepared. Worker commits happen only while that reservation is held; a pre-selection failure rolls workers back to prior ticks, modes and epochs, while a post-rename durability uncertainty reports every selected head, evicts the affected workers, and blocks new service mutations until catalog recovery. Successful restore invokes the existing lifecycle callback for every member so active manual recordings become partial. The fixture identity catalog is still separate, so this is not yet a heterogeneous fixture/connectome cross-store coordinator.

Shared creative capture does not read this barrier. Its [action-trace contract](CREATIVE_ARTIFACTS.md#action-trace-contract-version-1) can represent a research participant only as `declared-adapter-derived` when a separately declared adapter supplies the trace. No such adapter exists, and the barrier traces above carry clocks and substeps, not actions, so no full-connectome artifact, motor stream or creativity claim is produced.

This slice does not add a declared visual or contact adapter, an active-input pair measurement, biological validation, retained learning, chemistry or body control. Later slices must consume this persistence contract without silently substituting a fixture, dropping a full-graph step, sharing a graph namespace, or presenting a zero-drive result as embodiment or learning. A separate [render-only mixed world shell](MIXED_WORLD_SHELL.md) now shows research participants beside fixture sessions. It shows them only as labeled research markers, with no body, sensory input or motor output, and it has no mutation authority.

The targeted regression tests use tiny named graphs, temporary catalogs and injected worker scheduling. They cover staged capacity/history/durability refusal, projected file-bound refusal and cleanup, schema-1 reopen, malformed joint catalog rejection, complete membership and namespace validation, rollback after a second-worker failure, all-resting status, concurrent withdrawal/barrier reservations, recording invalidation, fresh paused epochs, rest/withdrawal and storage-fault recovery. They do not load the pinned full datasets, measure production pair capacity, run a simulation automatically, or establish a biological result.

## Barrier telemetry, measurement and capacity

Every shared session response carries `shared.telemetry` (kind `shared-barrier-telemetry`). It is produced by `server/shared-barrier-telemetry.js`, a reusable recorder with no participant or command authority, so later cross-store and mixed-world slices can use the same contract. There are four separate things here:

- **Queue and lag observation.** The registry reports each barrier's queue wait (time spent draining work already queued for the members), its prepare and commit phase durations, each member's own prepare/commit duration, and the order in which members completed each phase. The session adds the total wall time and `lagMs`, which is the wall time beyond the 5 ms world interval. Time between explicit requests is not lag, because no timer exists. Completion order is recorded only as an observation. Commits and traces stay in membership order, and the clocks are checked independently: every committed sample reports `substepValidation: "exact"` and five observed substeps per active member. A skipped or extra step is recorded as a failed `step-mismatch` sample with per-member skipped/extra counts, never as success.
- **Health.** `telemetry.health` reports `nominal`, `stale`, `pressure` or `fault`, with safe reason codes: `participant-fault`, `stale-epoch`, `resource-pressure`, `deadline`, `worker-failure`, `invalid-candidate`, `invalid-result`, `step-mismatch` or `participant-unavailable`. Pressure pauses are counted. Reading this state never pauses anyone. A faulted or stale participant still pauses the session only through the existing barrier/start path, and an explicit start clears the recorded fault and pressure reasons.
- **Active-pair measurement.** `POST /api/connectomes/shared/:id/measure` accepts `{protocolVersion, sharedId, worldEpoch, sequence, barriers}` with 10–1000 barriers. It requires an already started session with every member active; resting members are never measured. It runs complete barriers through the same validated path and samples process RSS between them. It stops at the first barrier failure, resource pressure or the 60 s deadline. The session is then paused (a failure or deadline uses an ordinary pause, pressure uses the pressure path), and the measurement is reported as `unavailable` with a `stopReason`. A deadline cannot interrupt an in-flight barrier, which remains bounded by the registry operation deadline. The measurement is zero-drive: no sensory input, stimulus, rendering or learning is present. The record keeps only stable IDs, dataset/model/graph hashes, the runtime, and barrier/wall/RSS summaries. Only the latest measurement is kept, in memory, and it is not persisted.
- **Configured and validated capacity.** `telemetry.capacity.configuredMaxResidents` is the operator ceiling from the population policy, not measured throughput. `validatedConnectomeCapacity` stays `null` with a reason (`no-measurement`, `measurement-incomplete`, `measurement-malformed`, `runtime-mismatch`, `membership-mismatch`, `not-pinned-full-graph`, `insufficient-barriers`) unless a complete measurement of at least 100 barriers meets all of these conditions:
  - it matches the live active membership exactly;
  - it matches the canonical pinned MaleCNS/BANC full-graph hashes and model IDs;
  - it was taken on the same Node version, platform and architecture.

  Tiny graphs, fixtures and reduced graphs cannot match a pinned full-graph hash, so they cannot validate capacity. A validated value describes only that zero-drive shared barrier on this runtime. It is not an admission authorization, a rendered or active-input capacity, or a larger-population claim. The population snapshot's own `validatedConnectomeCapacity` remains `null`.

`telemetry.resources` exposes aggregate counts, the pressure state and memory bytes, plus each member's dataset, model ID, status and trusted per-profile paused memory evidence. It never exposes directories, graph arrays, neural payloads or credentials. Malformed, non-finite, negative or non-monotonic timing, or a participant/order mismatch, is published as an `invalid-telemetry` sample with null timings. It does not affect the barrier outcome. History keeps at most 32 aggregate samples, and only the latest sample carries per-member detail, so a response stays bounded at 64 members. The full-connectome lab shows this as a collapsible, read-only panel with an explicit refresh (a GET) and a separate explicit measurement button.

Tests use tiny named graphs and injected scheduling. They cover completion-order reversal and injected queue delay while clocks stay at exactly five substeps, registry deadline rollback, invalid/non-finite values, the retention bound, reads that consume no sequence and make no worker call, fault and stale reporting without automatic pause, pressure counting, measurement bounds/deadline/pressure/failure stops, and capacity matching. **Negative result:** no measurement of the complete pinned MaleCNS/BANC pair was run for this change, so no validated shared capacity exists yet. The [zero-drive operating envelope](OPERATING_ENVELOPE.md) of two independently owned workers remains the only recorded full-graph pair result.
