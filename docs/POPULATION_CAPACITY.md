# Population capacity and admission

`server/population-capacity.js` supplies the resource policy used to guard explicit loads. Capacity settings are positive safe integers: `maxResidentFlies` defaults to one, `maxAggregateMemoryBytes` defaults to 512 MiB, and `minFreeMemoryBytes` defaults to 256 MiB. These are conservative operator defaults, not measured biological operating envelopes. The supervisor must persist validated settings before applying them; failed persistence leaves its previous settings intact. Backups must retain these local settings alongside identity checkpoints and validate them on restore.

A resident is any loaded individual, including a paused or faulted individual. Saved, unloaded identities do not consume a resident slot. Admission checks the current resident count, incremental memory footprint, aggregate supervisor/worker memory and current host free memory. Host free memory already reflects existing processes; their resident allocations must not be subtracted twice. The aggregate budget covers the supervisor and loaded workers. Incremental estimates account for dataset, worker, renderer and telemetry allocations; shared allocations may be excluded only when actually reused. Unknown or invalid measurements reject admission with an explicit reason. Full graph cropping, dropped neural steps and cloud compute are not capacity solutions.

Configuration changes never create, start, reset or evict individuals. Reducing capacity below current occupancy reports excess residents and blocks new loads. Explicit unload must durably checkpoint before releasing its slot; a failed write must retain the resident and previous durable checkpoint. Reload keeps the identity and checkpoint lineage and starts paused with a fresh command session. Load failures must not modify existing residents. The single PM2 application remains the supervisor; individual workers are not separate PortOS application registrations.

The snapshot separates configured capacity, resident/running/saved-unloaded counts, current memory pressure and validated connectome capacity. A universal validated resident count remains unknown: lightweight tests at one, two and four residents do not establish a capacity guarantee. The UI separately presents dated full-dataset workload evidence. A hard memory limit or unavailable monitoring data requires the supervisor to pause affected work. Future shared-world slowdown must use #20's fixed-step timing contract and must not skip neural steps.

## Evidence and remaining boundaries

The policy tests exercise invalid settings, unknown resources, exact headroom boundaries, paused-worker counting, explicit slot release, reducing and increasing limits, write failure and nonmutation of resident records. Integration tests are responsible for actual checkpoint/unload/reload and mixed-recipient policy isolation; the capacity module does not copy or overwrite stimulus ledgers. Each recipient continues to use the existing stimulus-policy machinery.

The published [single and paired operating envelope](OPERATING_ENVELOPE.md) records one zero-drive run each for complete MaleCNS, BANC and their pair on September 12, 2026, with exact runtime, hardware, graph/model provenance, memory and per-resident throughput. The separate [active-edge trial](VISUAL_CAUSAL_VALIDATION.md) used one worker at a time and produced a negative motor-readout result. Population capacity displays these historical workloads separately from current usage and configured limits. Neither establishes rendered, sustained-active or larger-population capacity on the current installation; admission still uses matching local paused memory evidence and fresh headroom.

The local setting file is `capacity.json` beside the identity store, with schema version 1. Writes use a flushed temporary file and atomic rename. Invalid or incompatible existing configuration stops initialization and remains available for repair; it is never replaced by defaults.

The synthetic-fixture probe constructs at most four detached paused runtimes (never advances them), retains their snapshots/checkpoints, and measures heap/RSS allocation growth. The whole batch delta multiplied by four is used as a conservative per-instance estimate. A 16 MiB observed allocation ceiling stops further samples; unavailable or nonpositive deltas leave the footprint unknown. This probe is limited to this small fixture and is not a generic safe probe for arbitrary dataset allocation. Real workers and incremental browser rendering require separate measurements before admission. Allocator behavior and garbage collection can produce inconclusive results, which must be reported rather than interpreted as zero-cost loading.

Full-connectome admission failures return HTTP 409 with a safe policy `code` and canonical `error` reason (`resident-limit`, `unknown-footprint`, `unknown-resources`, `aggregate-memory`, `memory-headroom`, or `invalid-residents`). Rejected admission does not create a worker or consume the recipient command sequence. Arbitrary worker, filesystem and storage errors remain generic; their messages cannot become public capacity reasons.
